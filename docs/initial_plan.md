## Motivation and System Objectives

Standard Retrieval-Augmented Generation (RAG) pipelines struggle with two fundamental bottlenecks when processing university-level coursework:

2. **Relational Context:** Standard RAG uses vector similarity. If a student queries how an algorithm taught in an advanced Machine Learning course connects back to a specific eigenvalue derivation from a previous Linear Algebra course, standard RAG fails to bridge the conceptual gap unless the text is semantically identical.

**The Objective:** To engineer a low-cost (or free), privacy-respecting pipeline that guarantees high-fidelity ingestion of technical documents and utilizes a Knowledge Graph (GraphRAG) to explicitly map inter-course relationships.

---

## Proposed Architecture and Toolchain

This pipeline is designed around a "Local Data, Cloud Inference" model. The data processing, storage, and retrieval orchestration occur locally, while the heavy lifting of inference is routed to a free-tier API.

### 1. Ingestion Layer: Baidu `Unlimited-OCR`

- **Why this tool:** Released in June 2026, `baidu/Unlimited-OCR` is a 3.3B parameter Vision-Language Model optimized specifically for generating clean Markdown and LaTeX from complex documents.
- **Key Advantage:** It utilizes Reference Sliding Window Attention (R-SWA), allowing for "one-shot long-horizon parsing." Instead of processing a PDF page-by-page (which breaks cross-page tables and footnotes), it can ingest up to ~40 pages in a single forward pass, maintaining a constant KV cache.
- **Data Flow:**
- PDFs are converted to images via `PyMuPDF`.
- `Unlimited-OCR` processes the images.
- A custom post-processing regex strips out the model's `<|det|>` bounding box tokens.
- The output is raw, highly accurate Markdown containing correctly formatted LaTeX blocks.

### 2. Storage & Interface: Obsidian

- **Why this tool:** Obsidian acts as the local, Markdown-native persistent state. It provides a visual interface for the data and explicitly supports bidirectional linking (`[[wikilinks]]`), which is vital for seeding the knowledge graph.
- **Data Flow:** The clean Markdown files generated by `Unlimited-OCR` are saved directly into the Obsidian vault, organized by course directories.

### 3. Orchestration & GraphRAG Layer: LlamaIndex `PropertyGraphIndex`

- **Why this tool:** While Obsidian plugins (like Simple Graph Builder) exist, building a custom Python script with `LlamaIndex` provides deterministic control over the chunking and graph extraction logic. LlamaIndex recently integrated native support for Obsidian vaults and Property Graphs.
- **Data Flow:**
- **Loading:** The `llama-index-readers-obsidian` module parses the vault. Crucially, it splits documents logically by Markdown headers rather than arbitrary character counts, and it natively extracts Obsidian's `[[wikilinks]]` as pre-defined graph edges.
- **Embedding:** A local, lightweight embedding model (e.g., `BAAI/bge-m3`) runs on CPU to vectorize the chunks without API calls.
- **Graph Extraction:** LlamaIndex's `PropertyGraphIndex` processes the chunks. It uses an LLM to extract entities (Nodes) and relationships (Edges), combining them with the manual `[[wikilinks]]` to build a localized Knowledge Graph.

### 4. Generation Layer: Google AI Studio (Gemini Free Tier)

- **Why this tool:** The Gemini API offers a generous free tier for the `gemini-2.5-flash` model, providing high throughput for both the graph extraction phase and the final query generation.
- **Data Flow:** When a user submits a query, LlamaIndex traverses the local Property Graph to retrieve interconnected context. Only this specific, localized context—along with the user query—is sent to the Gemini API for the final synthesized response.

## Tentative Layout and Workflow

To implement this, you will need a dual-environment setup: a local Python microservice for data processing and a UI (Obsidian) for interaction.

### Phase 1: The Ingestion Pipeline (Python / vLLM)

This script runs asynchronously when new course material is added.

1. **PDF to Image:** `PyMuPDF` converts the source document.
2. **OCR Inference:** The images are passed to the local `Unlimited-OCR` vLLM server.
3. **Sanitization:** Apply the OmniDocBench regex to remove `<|det|>` tokens.
4. **Save to Vault:** Write the output to `/obsidian_vault/Course_Name/Document.md`.

### Phase 2: The Indexing & Graph Construction (LlamaIndex)

This script builds the intelligence layer over your vault.

1. **Read:** `ObsidianReader` loads the vault, chunking by header and extracting `[[wikilinks]]`.
2. **Extract:** The Gemini API (via LlamaIndex) extracts entity triplets (e.g., `[Course A] -> utilizes -> [Algorithm X]`).
3. **Store:** The graph and vector embeddings are saved to a local disk storage context (e.g., `SimplePropertyGraphStore`).

### Phase 3: Query Execution (The User Loop)

When you are studying and have a question:

1. You query the LlamaIndex Python script (this can be executed via a simple terminal prompt or a custom Obsidian plugin that pings a local `localhost` port).
2. LlamaIndex queries the local Property Graph for the relevant nodes and edges.
3. The retrieved context is sent to the Gemini API.
4. The generated answer is returned to you.

## Constraints and Trade-offs

- **Hardware:** The ingestion phase (`Unlimited-OCR`) strictly requires a GPU with at least 8GB of VRAM. If this is unavailable, the ingestion layer must be offloaded to a cloud instance.
- **Free Tier Limits:** While the Gemini API is free, you must monitor the Requests Per Minute (RPM) limits, particularly during the Graph Extraction phase (Phase 2), as LlamaIndex will make multiple rapid API calls to build the triplets. You may need to implement a rate-limiting sleep function in your LlamaIndex setup.
- **Data Privacy:** Using the free tier of Google AI Studio means your query data may be used for model training. Do not process proprietary or sensitive personal data through this pipeline.
